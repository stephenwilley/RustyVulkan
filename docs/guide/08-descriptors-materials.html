Descriptors and materials

How a shader's set and binding numbers get connected to real buffers and textures, and how the renderer packages that up as reusable materials.

Overview The big picture

Chapter 6 showed shaders asking for resources by number: "set 0, binding 0 is a uniform buffer", "set 1, binding 0 is a texture". The shader doesn't know which buffer or which texture. Something has to fill in those slots before each draw. In Vulkan that something is a descriptor: a small, driver-defined record that points at a resource and says how it will be used. Three objects and one action are involved:

  • A descriptor set layout is the shape of a group of slots: "binding 0 is a uniform buffer used by both stages; binding 1 is a sampled image used by the fragment shader".
  • A descriptor pool is the memory that descriptor sets are allocated from, sized up front for how many sets and descriptors of each type you'll need. Pools let the driver hand out sets cheaply and free a whole group at once.
  • A descriptor set is one filled-in instance of a layout: an actual table of pointers.
  • Binding a set at draw time plugs that table into a numbered slot, so the shader's set = 1 now means this particular material's textures.

Grouping by frequency

Why two sets? Because some data is shared by everything drawn in a frame (the lighting and the shadow map) while some changes with every material (its textures). Keeping them in separate sets means switching material only replaces set 1. (Set numbers only mean something relative to a pipeline's layout: the sky and the grass have their own small sets with different contents.) And because the GPU may still be reading last frame's set 0 while the CPU prepares the next, there's one set 0 (and one uniform buffer) per swapchain image.

Two other small pieces complete the picture. A sampler describes how to read a texture (smooth or blocky filtering, whether coordinates wrap) and is a separate object from the image. A combined image sampler descriptor pairs one of each, and is what every texture binding in this renderer uses. And push constants, for a few bytes of per-draw data such as an object's matrices, skip descriptors entirely: their values are written straight into the command buffer.

Materials

RustyVulkan bundles "shaders + pipeline + texture descriptor set" into a material. A material manager makes sure each named material is created only once, and a texture cache makes sure each image file is loaded only once, even if several materials use it. The cache owns the images; materials just hold copies of their handles.

Coming from OpenGL

In OpenGL, you bound a texture to a numbered unit with glActiveTexture + glBindTexture, told the shader's sampler uniform which unit to use, and bound uniform buffers to indexed binding points with glBindBufferBase. A descriptor set is all of those bindings, prepared in advance as one object and switched in a single call. Sampler objects (glGenSamplers, GL 3.3) are the direct ancestor of VkSampler.

The shared sampler

Every material texture is read with the same settings, so the texture cache creates a single sampler on first use:

Linear filtering, repeating coordinates (needed for the tiled ground textures), no anisotropic filtering (a quality setting for surfaces seen at grazing angles), and max_lod 0, which means only ever sample the full-size image, since there are no mipmaps (Chapter 5). The shadow map has its own sampler, created in VulkanBase::new, which clamps at the edges instead of repeating.

Rust note · moves, and indices as IDs

request_material takes props by value, so the caller gives it up. Its String fields are then moved into Material::new: ownership of the heap text transfers, with no copy. That's the default for non-Copy types (Chapter 2), and the compiler rejects any later use of a moved-from value.

Using a Vec index as an ID, rather than a reference to the material, is a common Rust pattern. Scene objects can store a plain usize, and the borrow checker never has to reason about long-lived references into the vector. The cost is that nothing stops an index going stale (there's no generation counter), which is fine here because materials are never removed while the app runs.

Binding at draw time

The main pass (Chapter 12) switches pipeline and descriptor sets only when the material changes, then pushes per-object constants and draws:

cmd_bind_descriptor_sets binds the given sets starting at slot 0, against the pipeline's layout, which they must match (Chapter 7). set0_descriptor_sets[image_index] picks the global set belonging to the swapchain image being drawn. cmd_push_constants writes the 144 bytes of matrices and UV tiling directly into the command buffer.

Teardown order

Materials go first: each destroys its pool (which frees its set) and its layout and pipeline, and clear() then drops them, which frees their ShaderModules. Only then does the cache destroy the images their descriptors pointed to, and the material sampler. (The shadow sampler belongs to VulkanBase.) That's the rule from DEVELOPMENT.md: material descriptors must be released before cache teardown.

A simplification worth noticing

Every material creates its own descriptor set layout and its own one-set pool, even though all textured materials share the same layout shape. That's simple to own and destroy, but it means many tiny pools. A larger renderer would share one layout and allocate every material's set from a single pool.

Recap

  • Descriptors connect shader set/binding slots to real resources: layouts give the shape, pools provide the memory, sets are filled tables, and binding plugs them in.
  • For scene materials, set 0 is global (lighting uniform buffer and shadow map), one per swapchain image, and set 1 is per material (colour and normal textures). The sky and grass have their own sets. Push constants carry per-draw matrices.
  • One shared sampler serves all material textures; the shadow map has its own.
  • The material manager dedupes materials by name, and the texture cache dedupes images by path and owns them. Materials are torn down before the cache.
