Rust meets a C API

Vulkan is defined in C. This chapter shows how the ash crate presents it to Rust, and why, even in a "memory-safe" language, this codebase has to keep track of who destroys what by hand.

Overview Source walkthrough Recap

Overview The big picture

The shape of the Vulkan C API

Almost everything in Vulkan follows one pattern. To make an object, you fill in a "create info" struct describing what you want and pass it to a vkCreate… function. You get back a handle: an opaque number that names the object inside the driver. When you're finished, you pass that handle to the matching vkDestroy… function. Every call reports success or failure with a result code.

Objects depend on each other. A buffer is created from a device; a device from an instance. Vulkan's rule is that you must destroy them in the reverse order, children before parents, and never destroy something the GPU is still using. Break the rule and the behaviour is undefined: maybe nothing happens, maybe a crash, maybe a corrupted frame.

What ash adds, and what it doesn't

ash is a deliberately thin layer. Its functions correspond one-to-one with Vulkan's, and its structs have exactly the same fields. What it adds is Rust's vocabulary on top:

  • Result codes become Rust Result values, so a failed call is hard to ignore by accident.
  • Create-info structs come with sensible defaults, and optional "builder" methods that let the compiler check that the data a struct points at lives long enough.
  • Functions are grouped onto the object they belong to: device functions are methods on a Device, and so on.

What ash does not do is hide anything. Every call is still the raw Vulkan call, with all of its rules, which is why nearly every call is marked unsafe in Rust.

What Rust catches before you run

For a C programmer, the useful change is that ownership becomes part of the language. A vector owns its allocation; moving that vector transfers ownership without copying its elements. This deliberately invalid example demonstrates the check:

In C, two variables holding the same allocation's address can accidentally become two supposed owners, leading to a double free or use after free. Here the old name cannot be used. When upload_data goes out of scope, its CPU allocation is released once. Shared references let other code read the vector without taking ownership; an exclusive reference lets it change the vector. The compiler checks those relationships too. That removes a great deal of ordinary memory bookkeeping around the Vulkan calls.

Rust's safety net has a GPU-shaped hole

Rust's best-known feature is that it manages memory without a garbage collector. Every value has exactly one owner; when the owner goes away, the value is cleaned up automatically, at a predictable moment. That works perfectly for things Rust understands, such as strings, vectors and files.

A Vulkan handle, though, is just a number to Rust. Rust can't know that the number refers to a texture in GPU memory, that the device must outlive it, or that the GPU might still be reading it. So this codebase adopts a convention, stated in its own DEVELOPMENT.md: every Vulkan resource has exactly one owner in the code, and that owner destroys it explicitly, in the right order. Anywhere else a handle appears, it's merely borrowed.

Deeper dive

Entry, Instance, Device: three tables of functions

In C, you call free functions like vkCreateBuffer(device, …). ash makes the function lookup explicit with three types, each holding a table of function pointers for one level:

  • ash::Entry: functions that need no Vulkan object yet, such as listing layers and creating an instance. Entry::linked() uses the loader linked in at build time (the linked feature from Chapter 1).
  • ash::Instance: the instance handle plus functions that act on it (enumerating GPUs, creating a device).
  • ash::Device: the device handle plus every device-level function (create buffers, record commands, submit work).

Extensions, optional features outside core Vulkan, get their own small tables, created from the base ones. The window-surface, swapchain and push-descriptor functions are extensions, so VulkanBase::new builds loaders for them:

Rust note · struct literals, defaults and builders

Type { a: 1, b: 2, ..Default::default() } is struct update syntax: "these fields as given, everything else from the default value". Default is a trait, Rust's name for an interface that a type can implement; here it supplies the zero/empty value.

The difference matters. A raw .as_ptr() pointer in a struct literal is invisible to the compiler: if the vector it points into were freed before the create call, you'd pass a dangling pointer, just as in C. Builder methods take a Rust reference instead, and ash's structs carry a lifetime parameter so the compiler refuses to let the struct outlive the data it points at. This codebase mostly uses struct literals, so it keeps the pointed-to data in local variables that live until the call returns.

Vulkan extends structs through a pNext pointer chain: a linked list of extra structs hanging off the main one, used for features added after the original struct was defined. The builder push_next links one in safely, and calls can be chained to add several. Why it's all unsafe

Rust note · unsafe

Most Rust code is checked by the compiler for memory errors: no dangling pointers, no use after free, no data races. An unsafe { … } block doesn't turn those checks off. It permits a few extra operations the compiler can't verify, chiefly calling functions marked unsafe and following raw pointers. It's the programmer's promise that the rules those operations depend on hold.

Vulkan's specification lists thousands of "valid usage" rules: this handle must be alive, that image must be in the right layout, this buffer must not be in use by the GPU. Apart from the pointer lifetimes its builders track, ash can't check them, so it marks nearly every function unsafe. The compiler still checks the surrounding Rust, but the programmer must satisfy Vulkan's rules. The validation layers, enabled here in debug builds, detect many violations while the program runs (Chapter 3). They are a debugging aid, not a proof of correctness: for example, they cannot generally see the CPU overwriting mapped bytes that the GPU is still reading. Chapter 9 explains the waits that prevent that race.

Errors: Result and ?

Rust note · Result, ?, and Box<dyn Error>

A fallible function returns Result<T, E>, either Ok(T) or Err(E). You can't use the T without dealing with the possibility of E. Writing ? after a call means "unwrap the Ok value, or return the Err to my caller immediately". It replaces the C idiom of if (res != VK_SUCCESS) return res; after every line.

ash turns each VkResult into Result<T, vk::Result>, where vk::Result is the error code. Many functions here return Result<…, Box<dyn Error>> instead, meaning "any kind of error". dyn Error is a value of some type implementing the Error trait; Box puts it on the heap so different error types fit in one return type. Because vk::Result implements Error, ? (or an explicit .into()) converts it automatically, so different error types can flow out of one function.

Below, CString::new can fail with yet another error type (a string containing a zero byte), and the ? on the last line handles it the same way.

Borrowing

Rust note · references and borrowing

&T is a shared reference: a pointer that lets you read a value without owning it. &mut T is an exclusive reference that allows changes. The compiler enforces two rules: a reference never outlives the thing it points to, and while something is borrowed mutably, nothing else can access it.

Most functions in this codebase take the big objects by reference (&Instance, &ash::Device), because they only need to use them. Handles, being Copy (see below), are usually passed by value, like physical_device here:

Handles are just numbers

Rust note · Copy types, and why handles are one

Normally, assigning a Rust value moves it: the old variable can no longer be used, which is how Rust guarantees a single owner. Types marked Copy are the exception: small, plain values like integers that are simply duplicated.

Every ash handle type (vk::Buffer, vk::Image, vk::Fence…) is a Copy wrapper around a plain number or pointer. Copying one does not create a second GPU object, and letting a copy go out of scope does not destroy anything. That's exactly C's behaviour, and it's why ownership has to be a convention here rather than something the compiler enforces.

Drop: automatic clean-up, and its limits

Rust note · Drop

When a value's owner goes out of scope, Rust calls that type's Drop implementation, if it has one, and then drops each of its fields in turn. It's the same idea as a C++ destructor (RAII). It happens exactly once, at a point you can predict from the code.

Vulkan objects here aren't wrapped in individual Drop types. A wrapper would have to keep a copy of the ash::Device to call its destroy function, and cloning that copies only the function table; it doesn't keep the real Vulkan device alive, so nothing would stop the device dying first. Instead each owner has an explicit clean-up method, and Drop appears on the two owners at the top, which call those methods in the right order. Note that it logs the wait-idle error rather than returning it with ?: a destructor has no caller to report to, and panicking in a destructor while another panic is unwinding aborts the program. The allocator is stored as an Option so it can be destroyed in a chosen place. Option::take() moves the value out and leaves None behind, which is how you take ownership of a field when you only have &mut self.

VulkanBase itself lives inside App, which owns the renderers and resource managers built on top of it. After a drop body finishes, Rust drops the struct's fields in declaration order, which isn't the order Vulkan needs. When creation fails halfway

The harder case is a function that creates several objects and fails on, say, the third: the first two now need destroying, or they leak. The project's rule is to record ownership after each step and release what's been made if a later step fails. Here it is in the code that creates one uniform buffer per swapchain image:

Not finished yet

DEVELOPMENT.md is candid that this isn't applied everywhere. Some start-up paths, including much of VulkanBase::new, which uses ? after each step without unwinding earlier ones, and the grass upload code, don't yet release everything on a partial failure, and several helpers still panic on Vulkan errors. For a program that exits on any start-up error this costs little, but don't copy it wholesale.

Recap

  • ash mirrors Vulkan one-to-one, organised into Entry, Instance and Device function tables plus per-extension loaders.
  • Nearly every call is unsafe because Vulkan's rules can't be checked at compile time; validation layers detect many mistakes at run time, but correctness remains the programmer's responsibility.
  • Errors are Results, propagated with ? or matched when expected.
  • Handles are Copy numbers, so ownership is a convention: one owner per resource, destroyed in reverse dependency order.
