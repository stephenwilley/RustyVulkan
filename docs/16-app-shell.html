The app shell

The code that holds everything together: the window and its event loop, keyboard and mouse, shutting down in the right order, and packaging the result as a Mac app.

Overview Source walkthrough Recap

Overview The big picture

An event loop drives everything

A desktop program doesn't run in a straight line. It hands control to the operating system's event loop, which calls back into the program whenever something happens: the app is ready to start, a key is pressed, the mouse moves, the window is resized or closed, or it's time to draw. RustyVulkan uses winit for this. App implements winit's ApplicationHandler interface, a set of methods winit calls as those events arrive.

Controls

It's a first-person view: W A S D walk over the terrain, the mouse looks around (the pointer is hidden and locked to the window), U toggles between mouse-look and a free pointer for the ImGui menus, F switches fullscreen, and Escape quits.

Starting, failing and stopping

Everything Vulkan is built only once winit says the app is "resumed" and a window can exist. If anything goes wrong while building, or later while drawing, the error is stored, the loop is told to exit, and the program ends with a failure exit code rather than crashing or carrying on half-broken. On the way out, everything is destroyed in reverse dependency order, as Chapter 2 described.

A Mac app

A packaging script turns the build into RustyVulkan.app, a self-contained application that carries its assets, the Assimp library, the Vulkan loader and the KosmicKrisp driver inside it, so the receiving Mac needs neither Rust nor the Vulkan SDK. It targets Apple Silicon Macs on macOS 26 or newer.

Deeper dive

Running the loop

ControlFlow::Poll keeps the loop spinning instead of sleeping until the next input event, which suits a renderer that wants to draw continuously. run_app blocks until the loop exits; any fatal error stored along the way is then returned to main, which turns it into a failure exit status (Chapter 1).

Rust note · implementing a library's trait

impl ApplicationHandler for App { … } provides winit's trait methods for our type, the way a C program would fill in a table of callback function pointers, but checked by the compiler. Traits were introduced in Chapter 2, and trait objects with the render passes in Chapter 10. Methods the trait gives a default for, like device_event, needn't be written unless you want them.

Start-up in resumed

The order is the order of the guide: window, ImGui context, the Vulkan backend (Chapter 3), the ImGui renderer, the scene (Chapter 12), and finally the passes. The guard at the top matters because winit's contract allows resumed to be called more than once (on macOS it fires once, but on mobile platforms it fires whenever the app returns to the foreground), and rebuilding would replace live GPU resources. Events

about_to_wait runs when the loop has handled all pending events. Requesting a redraw every time is what keeps frames coming; each RedrawRequested then moves the camera and runs the render graph (Chapter 9). Resize handling was covered with the swapchain (Chapter 4): it records a request, updates the camera's aspect ratio, and ignores zero-sized (minimised) windows.

Rust note · an exit flag behind an Arc

The menu's Exit item sets exit_flag, an Arc<AtomicBool> that the redraw handler checks before drawing. AtomicBool can be changed through a shared reference, which is handy when the UI only has borrowed access to the app's state; Arc is a reference-counted pointer that lets the UI context hold its own handle to the same flag. The render graph hands the UI pass its own clone each frame. It's more than a single-threaded app needs, but it costs little and would stay correct if threads arrived.

Shutting down

App::drop (excerpted in Chapter 2) waits for the GPU, then releases the render passes, sky, grass, materials and textures, meshes and the ImGui renderer, and only then lets VulkanBase go, which destroys the device's own objects, the allocator, the device, the surface and the instance. Because the backend is moved out of its field and dropped inside drop's body, it's gone before Rust drops the remaining fields, including the window: the Vulkan surface is destroyed before the window it belongs to.

Packaging a Mac app

scripts/package_macos.sh builds a release binary and assembles the bundle. The core of it:

  • The executable goes in Contents/MacOS, the assets and an installable client driver (ICD) manifest in Contents/Resources, and the three libraries in Contents/Frameworks.
  • install_name_tool rewrites the executable's references to those libraries, which point at the build machine's Homebrew and SDK locations, to @executable_path/../Frameworks/…, so they're found inside the bundle wherever it's installed.
  • Everything is ad-hoc signed (signed with no developer identity): Apple Silicon only runs signed code, and rewriting the library references invalidated the original signature. It isn't notarised (checked by Apple), so a recipient may need to right-click and choose Open the first time (PACKAGING.md).

Recap

  • App implements winit's ApplicationHandler. Start-up happens once in resumed; about_to_wait requests a redraw every iteration, and each redraw runs one frame.
  • Mouse look uses raw device motion; window events go to ImGui first; focus loss clears movement; U toggles the pointer for the UI.
  • Errors are stored, end the loop, and become a failure exit code. Teardown runs in reverse dependency order, with the surface destroyed before the window.
  • The packaging script builds a self-contained, ad-hoc-signed .app carrying assets, Assimp, the Vulkan loader, KosmicKrisp and the ICD manifest that main.rs selects.
