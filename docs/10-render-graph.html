The render graph

How a frame is split into passes, how each image is moved into the right layout for each one, and how a missing piece of that bookkeeping turned into a real bug.

Overview Source walkthrough Recap

Overview The big picture

Three passes

Every frame is drawn in three passes, each a stretch of rendering into a particular set of images:

  1. Shadow pass: renders the scene's depth from the sun's point of view into a shadow map, four times over (Chapter 11).
  2. Main pass: draws the sky, the objects and the grass into a colour image and a depth buffer, reading the shadow map as it goes (Chapter 12).
  3. UI pass: draws the ImGui panels on top of the finished scene (Chapter 15).

Images change jobs, so they change layouts

Chapter 5 introduced layouts: each kind of use wants an image's data arranged a particular way. The shadow map is a depth target in pass 1, then a texture in pass 2. The swapchain image is a render target, then something to hand to the display. Every change of job needs a barrier, which does three things at once:

  • Waits: work at some earlier stage must finish before work at some later stage starts (an execution dependency).
  • Publishes: writes made before the barrier become visible to reads after it (a memory dependency). GPUs have caches, and without this a later pass could read stale data.
  • Rearranges: moves the image from its old layout to its new one.

Each side of a barrier is described with a stage (where in the GPU's pipeline) and an access (what kind of reading or writing). Getting them too broad wastes performance. Getting them too narrow is a bug that may only show up on another GPU, months later.

What the "render graph" does

Rather than hand-writing every barrier, each pass declares which images it uses and how. The render graph runs the passes in order, remembers each image's current layout, access and stage, and inserts exactly the barriers needed between one pass and the next. DEVELOPMENT.md is careful to call it "a linear pass scheduler, not a general graph compiler". It doesn't reorder passes or share memory between images. It just keeps the bookkeeping honest.

Anti-aliasing and the resolve

With multisample anti-aliasing (MSAA) on, the main pass draws into separate images that store several samples per pixel. At the end of the pass, each pixel's samples are averaged into the single-sample swapchain image: the resolve. The multisampled images are then thrown away; only the resolved result is kept.

What a pass looks like to the graph

Rust note · traits and trait objects

A trait is a set of methods a type promises to provide, like an interface. Methods with a body, such as uses_attachment and cleanup, are defaults a type may override. The graph stores its passes as Vec<(RenderPassNode, Box<dyn RenderPass>)>: each is a heap-allocated value of some type implementing the trait, called through a table of function pointers, much like a C++ virtual call. That's how three different pass types share one list.

Starting each frame

The graph tracks each attachment's state as it goes. At the start of a frame every image is treated as UNDEFINED: its old contents are thrown away, since every pass here clears or overwrites its images anyway. Coming from OpenGL

None of this existed in OpenGL. Render-to-texture with an FBO "just worked" because the driver tracked every image's state and inserted the equivalent of these barriers itself. That tracking is a large part of what made OpenGL drivers heavy, and it's exactly the work Vulkan makes the application do.

Barriers between passes

Before each pass records, the graph compares what the pass wants with each image's current state:

If the layout or access differs, it records a transition from the current state to the new one, deriving the destination stage from the access type, and updates its record. All the transitions for one pass go into a single vkCmdPipelineBarrier2 call, with each image's barrier carrying its own stages:

synchronization2

vkCmdPipelineBarrier2 takes a DependencyInfo listing barriers that each pair their own source and destination stage and access masks, and queue_submit2 does the same for semaphores. Each barrier reads as one self-contained statement of what waits for what, which makes mistakes easier to spot.

Following the shadow map through a frame shows it working. Before the shadow pass: UNDEFINED → depth attachment, writing. Before the main pass: depth attachment → shader-read-only, so the main pass's fragment shaders wait for the shadow pass's depth writes to finish and be visible. The UI pass also declares shader-read access for its cascade preview. That matches the state established by the main pass, so it samples the same image without another transition. Declaring the read keeps this dependency visible to the scheduler even when the preview panel is closed.

The swapchain image shows one more rule. The UI pass keeps the same layout, but it loads the main pass's result and blends over it, so it declares read as well as write access. That difference is what makes the graph insert a barrier, so the UI can't read the image before the main pass has finished writing it.

Recap

  • A frame is three passes in fixed order: shadow, main, UI. Each declares the attachments it uses and the layout and access it needs.
  • Barriers wait, publish writes, and change layouts. The graph tracks every attachment's state and inserts the barriers between passes.
  • Each image's first barrier in a frame waits for whatever used it last, and a pass that reads an image declares it, so it waits for the writes before it.
  • With MSAA, the main pass draws into multisampled images and resolves into the swapchain image, discarding the samples. A final barrier readies the image for presentation.
