Shaders

How GLSL source becomes something Vulkan will accept, how the program loads it, and how a shader finds the data it needs, read through the renderer's main pair of shaders.

Overview Source walkthrough Recap

Overview The big picture

Shaders are the small programs the GPU runs for you: a vertex shader once per vertex, to work out where it lands on screen, and a fragment shader once per covered pixel, to work out its colour. RustyVulkan writes them in GLSL, the same C-like language OpenGL used.

If you last used OpenGL's fixed-function pipeline, think of the vertex shader as replacing the built-in matrix transform, and the fragment shader as replacing the built-in lighting and texture combination. You write the rules now. The vertex shader produces clip-space coordinates; the hardware clips triangles and turns them into fragments, interpolating values such as texture coordinates across each triangle. The fragment shader chooses each fragment's colour, which still has to pass depth testing and blending before reaching the image. GLSL looks much like C, with vector and matrix types such as vec3 and mat4 built in.

Compiled before the program runs

OpenGL took shader source text at run time and handed it to the driver's built-in compiler. Every vendor's compiler was different, so a shader that worked on one GPU could fail to compile, or behave differently, on another, and compiling cost time while the program was running.

Vulkan drivers don't accept GLSL at all. They take SPIR-V, a compact binary intermediate form defined by Khronos, much as a Java virtual machine takes bytecode rather than Java. Turning GLSL into SPIR-V is done ahead of time by a separate compiler. In this project that happens during cargo build.

How a shader gets its data

A shader can't call back into your program. Everything it needs has to be wired to it, and Vulkan offers three routes, each labelled with a number in the GLSL that the Rust side must match:

RouteGLSL labelGood forSet up in
Vertex attributeslocation = Nper-vertex data: position, normal, UV…Ch. 7
Descriptorsset = S, binding = Bresources: uniform buffers, texturesCh. 8
Push constantspush_constanta few bytes per draw, such as an object's matricesCh. 12

Data passed from the vertex shader to the fragment shader is matched by location too, and the fragment shader's output at location = 0 is the colour written to the image being rendered.

The build script

Rust note · build scripts

If a crate has a build.rs at its root, Cargo compiles and runs it before compiling the crate itself. It's an ordinary Rust program, with its own dependencies (shaderc is listed under [build-dependencies] in Cargo.toml). It talks back to Cargo by printing specially formatted lines such as cargo:rerun-if-changed=…. Think of it as the bit of a Makefile that generates files, written in Rust.

The script starts with an explicit list of shader sources:

As the comment says, the list doubles as a manifest. For each entry, the script tells Cargo to rerun it if that file changes, works out the shader stage from the extension, and compiles:

set_target_env(Vulkan, 0) selects Vulkan's flavour of GLSL, which adds things OpenGL GLSL lacks, such as descriptor set numbers and push constants. The 0 means the default target, Vulkan 1.0's SPIR-V, which is all these shaders need. (shaderc is Google's wrapper around glslang, Khronos's reference GLSL compiler.) The output goes to shaders/ under Cargo's OUT_DIR, inside target/. Failures use expect and panic!, which abort the build with the compiler's message. That's exactly right for a build script: a shader typo shows up as a build error, not a run-time surprise.

The script also generates a Rust table using include_bytes! for each compiled shader. ShaderStageInfo includes that table with include!(concat!(env!("OUT_DIR"), "/shader_assets.rs")). Both macros run during Rust compilation: the finished executable contains the SPIR-V and needs no shader files at run time. Add a shader to SHADERS to compile and embed it; after editing GLSL or the shared include, rebuild to update the executable.

Models and textures still come from external assets, so launch from the repository root or the packaged application as described in Chapter 1.

Rust note · let-else

let Some(shader_kind) = shader_kind else { continue; }; either unpacks the value or runs the else block, which must leave the current scope (here, skip to the next shader). It avoids nesting the rest of the loop inside an if let.

The same script also finds the Vulkan loader on macOS so the linked build of ash (Chapter 1) can link against it:

It tells the linker where libvulkan.dylib is, and adds an rpath so the finished program can find it again at run time.

The six lit fragment shaders include assets/shaders/global.glsl, which declares their common lights, cascade counts and global uniform block. The build script resolves this include and tells Cargo to watch it, so an edit recompiles the shaders. Loading SPIR-V

At run time, ShaderStageInfo::load looks up embedded SPIR-V by name and records which stage (vertex or fragment) it's for:

SPIR-V is a sequence of 32-bit words, and Vulkan wants it as a pointer to u32s. ash::util::read_spv decodes the embedded bytes into a properly aligned Vec<u32> and checks the SPIR-V header, which is safer than reinterpreting raw bytes. Nothing has been given to Vulkan yet: the words just sit in memory.

They reach the driver when a pipeline is created (Chapter 7). Each pipeline stage is described by a PipelineShaderStageCreateInfo, and with the VK_KHR_maintenance5 extension (Chapter 3) the SPIR-V can be chained straight onto it as a ShaderModuleCreateInfo, using push_next from Chapter 2:

The driver compiles the stage as part of building the pipeline, so there's no separate shader object to create first and destroy afterwards. Both structs only borrow: the stage info points at the module info, which points at the words, so a pipeline builder keeps all three alive until create_graphics_pipelines returns.

Rust note · lifetimes in signatures

The 'a in to_create_info ties the returned struct to the &'a mut module info it chains, so the compiler rejects any use of the stage info after the module info has gone. <'_> is the same lifetime parameter carried by ash structs (Chapter 2), left for the compiler to infer. The entry-point name, c"main", is a &'static CStr: a C string literal compiled into the binary, valid for the whole run.

Coming from OpenGL

There's no equivalent of glLinkProgram here. In OpenGL, linking joined the stages and checked their interfaces. In Vulkan, that joining happens when a pipeline is created (Chapter 7). OpenGL 4.6 can also load SPIR-V, through GL_ARB_gl_spirv; in Vulkan it's the only way. (macOS's OpenGL stops at 4.1, so never had it.)

Reading the main vertex shader

main.vert and main.frag draw the textured, normal-mapped objects: the test cubes, and imported models that have textures, such as the marble sphere in the screenshot:

  • Push constants (the first line): two matrices and a UV tiling factor, sent with each draw. mvp takes a vertex all the way to the screen; mv takes it into view space, where the camera sits at the origin, which is where lighting is computed. The fragment shader declares the same block without uv_tiling; that's legal, because each stage may declare just the leading part of the push-constant range it uses.
  • Inputs at locations 0–5: exactly the six fields of the Rust Vertex struct from Chapter 5, in the same order.
  • Outputs at locations 0–4, received by the fragment shader at the same locations: UV, the tangent frame for normal mapping, and the view-space position.
  • Normals are transformed with mat3(mv). Strictly, normals need the inverse-transpose of that matrix, but the two agree (after normalize) whenever the scale is uniform, and the scene's Transform type only allows uniform scale. The comment records that assumption.
  • gl_Position is the built-in output for the clip-space position, as in OpenGL.

The UV flip (1.0 - y) is commented "for Vulkan", but whether a flip is right depends on the incoming UVs. Vulkan, like image files, puts texture coordinate (0, 0) at the top-left. The flip suits UVs written with OpenGL's bottom-left origin, the convention Assimp's loaders usually deliver. Vulkan's coordinate conventions differ from OpenGL's in several ways, covered with the camera in Chapter 12.

The fragment shader's inputs

This is the descriptor side of the table above. Set 0 is global, shared by every object in a frame: a uniform buffer of lighting data (binding 0) and the shadow map (binding 1). Set 1 is per-material: a colour texture and a normal map. Grouping resources into sets by how often they change lets the renderer swap materials without touching the global data (Chapter 8).

std140 fixes the buffer's memory layout by strict rules: for instance, a vec3 is aligned like a vec4, to 16 bytes. The Rust struct that's copied into this buffer each frame (Chapter 5) has to reproduce that layout:

std140 is a contract, and the Rust side reproduces it by hand with explicit _pad fields and align(16). Compile-time assertions in gpu_data.rs check the Rust sizes and offsets the GLSL block expects. When changing this interface, update both declarations together: otherwise the shader silently reads shifted values. cascade_splits shows the care needed: it's a vec4 in GLSL because a GLSL float[4] would give each element 16 bytes under std140 and no longer match Rust's 16-byte [f32; 4].

The tail shows the same trap. The GLSL declares the padding after light_count as three separate uints. A single uvec3 would be aligned to 16 bytes, leaving a gap and making the shader's block 16 bytes longer than the Rust struct's [u32; 3]. This vec3-aligns-to-16 rule is one of the most common sources of garbled uniform data, in OpenGL as well as Vulkan.

Rust note · align

#[repr(C, align(16))] keeps C layout and also forces the struct's alignment, and so its size, to a multiple of 16 bytes. The constants in the array sizes, such as crate::app::app::MAX_LIGHTS, are full paths from the crate root. They must equal the #defines in global.glsl.

Recap

  • Vulkan consumes SPIR-V, not GLSL. build.rs compiles every listed shader with shaderc during cargo build, so shader errors are build errors.
  • ShaderStageInfo loads a .spv file. Its SPIR-V is chained into pipeline creation, and stages are joined there rather than linked into programs.
  • Shaders get data through vertex attributes (location), descriptors (set, binding) and push constants, and the Rust side must match each one by hand.
  • Uniform buffer layouts follow std140, mirrored in Rust with repr(C), alignment and explicit padding.
