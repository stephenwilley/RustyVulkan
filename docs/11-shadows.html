Shadows

Cascaded shadow maps: drawing the scene from the sun four times, and using the result to decide which pixels the sun can't reach.

Overview Source walkthrough Recap

Overview The big picture

Shadow mapping in two steps

A point is in shadow if something sits between it and the sun. Shadow mapping answers that with two renders:

  1. From the sun. Render the scene's depth from the sun's point of view, keeping only distances, no colour. The result, the shadow map, records how far the sunlight travels before it hits something, for every direction it can come from.
  2. From the camera. While shading each pixel, work out where that point would land in the shadow map and how far it is from the sun. If the map holds a nearer distance, something blocked the light first, so the point is in shadow.

The sun is so far away that its rays are effectively parallel, so step 1 uses an orthographic projection, a box rather than a pyramid.

Why four of them

A shadow map is an image, so its detail is limited by its texels (texture pixels). One map covering 75 metres of meadow would spread its 2048 × 2048 texels thinly, and near the camera, where a texel covers a large patch of the screen, shadows would look blocky. Cascaded shadow maps fix that. The camera's view (its frustum, the truncated pyramid of space it can see) is sliced by distance into four ranges, and each gets its own shadow map, fitted tightly around just that slice. The nearest slice is small, so its map is detailed; the farthest is large and coarse, which doesn't matter at that distance.

The screenshot on the cover shows them in its "Shadow Cascades" panel: four depth images, darker meaning nearer the sun. Cascade 1 covers only the ground right in front of the camera; by cascade 4 the hut is a small shape in a wide view of the valley.

Softening the edges

A single shadow-map lookup gives a hard, jagged edge. The shader instead takes six lookups in a small pattern around the point and averages the answers, a technique called percentage-closer filtering (PCF), which turns the jaggies into a slightly soft edge.

Deeper dive

Where to split

Evenly spaced splits waste the near cascades on too much distance; purely logarithmic ones (each slice a fixed multiple of the last) squeeze the first slice to almost nothing. This blends the two, 65% logarithmic, over the range from the camera's near plane to the shadow distance (75 m by default, set in EngineSettings). With the default 0.5 m near plane, the slices end at about 7.9, 17.3, 33.8 and 75.5 m; a purely logarithmic split would end the first at 1.75 m. Beyond the last slice, nothing is shadowed.

Rust note · building arrays from a closure

std::array::from_fn(|index| …) builds a fixed-size array by calling the closure once per index, with the array's length taken from the return type, here [f32; SHADOW_CASCADE_COUNT]. In compute_shadow_cascades below the same function is used with a closure that modifies a captured variable, slice_near, so each cascade starts where the previous one ended. Rust allows that because from_fn accepts a closure that may mutate what it captures (an FnMut), and it calls it in index order.

Fitting a light box around one slice

fit_frustum_slice starts by finding the eight corners of the slice in world space, using the camera's position and axes read from the inverse of the view matrix. It then wraps them in a sphere:

The sphere's radius sets how far the box reaches towards the sun, below. The light view itself deliberately depends only on the sun's direction: it sits at the world origin looking along the sunlight, and never moves with the camera.

In that fixed light space, the slice's corners give a rectangle; the box is made square, sized to the larger span, and its centre is snapped to a whole number of texels. Because the light space never moves, the snapped grid is fixed in the world: as the camera walks, the box jumps by exactly one texel at a time, so a shadow edge stays on the same texels instead of crawling. (Rotating the camera still changes the box's size slightly, so turning can still shimmer a little.)

The depth range reaches well beyond the slice towards the sun (by the sphere's radius plus a metre), so a tall object outside the slice can still cast a shadow into it. cgmath builds OpenGL-style matrices, so the same fixed matrix the camera uses (Chapter 12) remaps depth from OpenGL's −1..1 to Vulkan's 0..1. Each cascade keeps two matrices: one from world space, for drawing the shadow map, and one from the camera's view space, for the shader that reads it, which works in view space throughout.

Depth bias pushes the stored depths slightly further from the light, more so on surfaces seen at a glancing angle (the slope factor). Without it, a lit surface compares against its own depth, loses to limited precision on a patchy, angle-dependent basis, and is covered in stripes known as shadow acne.

The culling may look backwards. The comment explains it: unlike the camera's, this projection isn't flipped in Y, which reverses which way round triangles appear, so FRONT here removes the faces pointing away from the light.

Recording draws every visible scene object four times, once per cascade, each into one layer of the shadow array through that layer's own view (Chapter 10):

ShadowPushConstants stores just one matrix on the stack; bytemuck::bytes_of passes its bytes without a per-draw allocation. The matrix is light-space projection × model, for each object part. Note that the grass isn't drawn here: dense vegetation doesn't cast shadows into the map in this renderer.

Coming from OpenGL

The OpenGL version is the same idea: an FBO with a depth texture attached and glDrawBuffer(GL_NONE), rendered once per cascade, perhaps into the layers of a GL_TEXTURE_2D_ARRAY. glPolygonOffset is the depth bias.

Reading the shadow map

The main pass's fragment shader (Chapter 6) calls shadow_factor with the fragment's view-space position. Then come the PCF taps:

Each tap samples the cascade's layer of the array at a small offset, measured in texels, and compares the stored depth with the fragment's own (minus a tiny extra bias). Lit taps count 1, shadowed ones 0.4, so a point in full shadow keeps 40% of the sun's light: a simple stand-in for light bounced in from the sky. Points outside every cascade, or outside the chosen cascade's map, count as lit.

Coming from OpenGL

OpenGL renderers usually let the hardware do the comparison, with a sampler2DShadow and GL_COMPARE_REF_TO_TEXTURE, often getting a free 2×2 filter too. Vulkan has the same feature (a sampler with compare_enable), but this code compares by hand. The comments say it's a "compat path for platforms without compare samplers", presumably a precaution for the portability drivers of Chapter 3.

Keeping the math honest

Shadow fitting is pure arithmetic on the CPU, so it can be tested without a GPU (tests are explained in Chapter 4). This one checks the snapping: it moves the camera without turning it and checks that every cascade shifted by a whole number of texels:

The others check that the splits increase and end at the shadow distance plus the near plane, that every cascade still contains all eight corners of its slice, and that no matrix element is infinite or NaN.

Recap

  • Shadow mapping renders depth from the sun, then compares each shaded point's light-space depth against it.
  • Four cascades split the view by distance (blending linear and logarithmic spacing), each with a square orthographic box around its slice, snapped to texels in a light space fixed to the world.
  • The shadow pass is depth-only: one vertex attribute, no fragment shader, depth bias, drawn once per array layer.
  • The main shader picks a cascade, projects into it, and averages six manual comparisons (PCF); shadowed areas keep 40% of the sunlight.
