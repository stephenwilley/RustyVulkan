Grass

Drawing about 3.7 million blades of grass at interactive frame rates: one tiny mesh, a lot of compact per-blade data, culling, levels of detail, and wind computed on the GPU.

Overview Source walkthrough Recap

Overview The big picture

Instancing

The meadow in the screenshot holds about 3.7 million blades (3,661,366, to be exact) of grass and 6,570 flower stalks. Drawing each as its own object, with its own draw call, would bury the CPU. Instead the renderer uses instancing: one draw call says "draw this blade mesh N times", and the GPU runs the vertex shader for every vertex of every copy, telling it which copy (instance) it's working on. The blade's shape is stored once, ten vertices. Each instance adds just 16 bytes (half what plain floats would take), holding where its root is, how tall, which way it faces, how wide, a tint, and a wind phase. The vertex shader combines the two.

Coming from OpenGL

This is glDrawElementsInstanced with a second vertex buffer advanced by glVertexAttribDivisor(…, 1). In Vulkan the "divisor" is the binding's input rate, INSTANCE, fixed in the pipeline (Chapter 7).

Only draw what's near and visible

Even instanced, 3.7 million blades every frame would be wasteful, because most are behind the camera or far away. So the field is cut into a 32 × 32 grid of 5 m chunks, and each chunk's blades are stored together. Each frame the CPU checks every chunk against the camera's view, skips those outside it or over 100 m away, and chooses a level of detail (LOD) for the rest by distance: near (up to 12 m), medium (up to 24 m) and mid (up to 100 m, half the blades):

The chosen draws are written into a buffer as indirect draw commands: small records holding the same parameters as a draw call. The GPU reads its draw parameters from that buffer, and with the "multi-draw" feature, one call can issue all of a LOD's chunk draws.

Wind

The blades move. Rather than updating 3.7 million positions on the CPU, the vertex shader bends each blade every frame from a small, tiling noise texture (the wind map), scrolled over time: broad bright patches become gusts sweeping across the field, with finer turbulence and a gentle constant sway layered on top.

Deeper dive

The grass code is a parent module, grass.rs (the renderer), with five submodule files: generation.rs, upload.rs, pipeline.rs, wind.rs and tests.rs, each declared with mod (Chapter 1) and pulling in the parent's items with use super::*. The tests live in their own file but are still only compiled under #[cfg(test)] (Chapter 4).

Per-vertex and per-instance data

A GrassVertex is a point on the shared blade: 28 bytes, ten of them. A GrassInstance is eight 16-bit numbers. Each is a fraction of a known range stored as an integer from 0 to 65 535 (a UNORM16 value), which the GPU turns back into a float between 0 and 1 automatically. The packing is plain arithmetic:

Across a 161 m field, 16 bits gives a position step of about 2.5 mm, which is plenty. Packing halves the instance buffer compared with 32-bit floats: about 59 MB instead of 117.

The pipeline describes two bindings, one stepped per vertex and one per instance, and tells Vulkan the instance attributes are R16G16B16A16_UNORM:

Generating the field

The field is a 1792 × 1792 grid with two candidate roots per cell, nudged by a hash so the rows don't show. Each candidate survives with a probability equal to the grass density there, and the code skips clearings around the hut, cubes and sphere:

That density is the terrain's own grass_density_at (Chapter 13), pre-sampled into a coarse 129 × 129 map for speed, times a fall-off that thins the field to 30% towards its edges. hash01 is a hash like the terrain's, with a "stream" number so that each property of a blade gets an independent random value. The ground height comes from the same height function as everything else, plus 3 mm.

One trick lets every LOD share a single instance buffer:

Within each chunk, a stable random half of the blades is stored first. The "mid" LOD draws just that first half of the chunk's range; the near LODs draw the whole range. Neither needs its own copy of the data.

In the vertex shader

grass.vert first decodes the instance, using the same field bounds the Rust packing used:

The bounds are written in both languages (INSTANCE_X_RANGE and friends in Rust, the literal mix(-80.5, 80.5, …) here), so changing one without the other would misplace the whole field. grassParams.z is the LOD value from the push constants, 0, 0.5 or 1 for near, medium and mid; it widens blades by up to 50% and calms their fine sway as detail drops. Then the wind:

Two samples of the wind map, scrolling at different speeds and scales, give a gust strength (broad) and turbulence (detail). A continuous sway built from smoothed triangle waves runs underneath. The total bend grows with the square of height up the blade, so roots stay put and tips move most, and the tip drops by 12% of the bend to avoid stretching the blade. The wind map itself is a 128 × 128 noise image with two channels in use, generated on the CPU and uploaded once.

Lighting a ribbon

A blade is a flat, zero-thickness ribbon, drawn with no back-face culling so it's visible from both sides. Its true normal would make a whole blade go dark at once when it turned edge-on to the sun, so the vertex shader bends the lighting normal 62% towards straight up, a common vegetation cheat. Grass receives shadows (its fragment shader has its own copy of the cascade lookup) but doesn't cast any.

Choosing what to draw each frame

Every chunk is tested each frame. chunk_intersects_frustum transforms the eight corners of the chunk's box (including the real height range of its ground and blades) to clip space, and rejects it only if all eight lie outside the same clip plane, a conservative test with no plane maths. The chunk beneath the camera is always retained as an extra precaution. The survivors are sorted nearest first, so the depth test discards hidden blades early. Then each chunk becomes one draw command for its LOD, plus one in a separate list if it has reeds within 64 m:

first_instance is where the chunk's blades start in the shared instance buffer, so no data moves; only this 20-byte command is written each frame, into a mapped buffer belonging to the current swapchain image (Chapter 9).

Submitting the commands

The preferred path issues each LOD's commands with one cmd_draw_indexed_indirect, in batches no larger than the device's limit. Without multi-draw, it issues them one at a time.

The first branch is a fallback for GPUs that lack the drawIndirectFirstInstance feature, which indirect commands need in order to start at a chunk's first instance. There, the same draws are recorded directly with cmd_draw_indexed from the CPU-side list.

The draw itself binds the near pipeline, set 0 plus the wind map's set, the push constants (camera matrices, time, wind strength and LOD), and two vertex buffers. The blade mesh is binding 0, and the shared instance buffer is binding 1. GrassPushConstants names time, wind strength and LOD explicitly. Its last four floats match the GLSL grassParams vector, with offsets checked alongside the scene layout in gpu_data.rs:

The same pattern repeats for the medium LOD (a different blade mesh), the mid LOD (its own pipeline, using the cheaper grass_mid.frag), and the reeds, which use a six-sided stalk with a capsule-shaped flower head and their own instance buffer. The whole vegetation block is bracketed by GPU timestamps, which feed the profiler's vegetation figure where the GPU can time it separately (Chapter 9).

Rust note · raw pointers in a struct

IndirectBuffer keeps the mapped memory as mapped: *mut vk::DrawIndexedIndirectCommand, a raw pointer. Unlike a reference, Rust doesn't track its lifetime, so writing through it (copy_nonoverlapping) is unsafe, and the type is not automatically shareable across threads. That suits a value owned and used by one renderer on one thread.

Recap

  • Instancing draws one shared blade mesh millions of times. Each blade is 16 bytes of UNORM16-packed data, expanded in the vertex shader.
  • The field is generated once, deterministically, from the terrain's density and height functions, and stored chunk by chunk with a "mid" subset first so all LODs share one buffer.
  • Each frame the CPU culls 1,024 chunks, picks a LOD by distance, and writes indirect commands that select each chunk's range with first_instance.
  • Wind is two scrolling samples of a small noise texture plus a triangle-wave sway, bending blades more towards the tip.
