Surfaces and the swapchain

How finished images get from the GPU into the window, the choices that involves, and what happens when the window changes size.

Overview Source walkthrough Recap

Overview The big picture

Vulkan by itself knows nothing about windows. It can render into images in GPU memory, but showing one on screen is the operating system's job. Two objects bridge the gap.

A surface is the window as Vulkan sees it: a target that the system's compositor (the part of the OS that assembles all the windows into the final screen image) can display. On a Mac it wraps the window's Metal drawing layer. The surface is also what you ask about capabilities: which pixel formats it accepts, its current size, how images can be handed over.

A swapchain is a small set of images, owned by the system's presentation machinery, that take turns being shown on that surface. You don't draw into the window directly. Each frame, you acquire one of the swapchain's images, render into it, and present it, which hands it back to be displayed. Meanwhile, the image you presented last is on screen, and at most one other may be waiting its turn.

Choices made when building it

  • How many images. This renderer asks for three, within whatever range the surface allows.
  • Pixel format. It prefers 8-bit blue-green-red-alpha, the common native format for displays.
  • Size. The window's size in actual pixels. On a Mac's high-density "Retina" display that's twice the size macOS reports for layout.
  • Present mode, meaning how presented images reach the screen. FIFO is a queue drained once per display refresh: classic vsync, always available. Mailbox also waits for the refresh but replaces a waiting image with a newer one. That cuts latency without tearing, the visible seam you get when the screen switches images mid-refresh. RustyVulkan uses mailbox when offered, otherwise FIFO.

When the window changes

Swapchain images have a fixed size. When the window is resized, the swapchain no longer matches, and Vulkan says so by reporting it "out of date". The renderer then builds a new swapchain and throws away the old one, at a moment when nothing is mid-frame. Minimising the window is a special case: a zero-sized window can't have a swapchain at all, so the redraw handler skips drawing entirely until it comes back.

This renderer also keeps a pair of window-sized multisampled images alongside the swapchain, used when anti-aliasing is on: one for colour and one for depth. They store several samples per pixel for anti-aliasing, and the result is averaged down into the swapchain image at the end of the main pass (Chapter 10). Because they must match the window's size, they're created, recreated and destroyed together with the swapchain.

Deeper dive

Making the surface

As Chapter 3 showed, the surface is created before a GPU is chosen. The ash-window crate does the platform-specific part:

display_handle() and window_handle() come from the raw-window-handle crate, a common vocabulary that windowing libraries (here winit) and graphics libraries (here ash-window) both speak. On macOS, ash-window uses them to find the window's CAMetalLayer and creates the surface with the VK_EXT_metal_surface extension.

Format

The preferred format is B8G8R8A8_UNORM in the standard sRGB colour space. If the surface doesn't offer it, the first supported format is used; if it offers none at all, that's an error. The very first branch handles an old convention where a surface reported one UNDEFINED format, meaning "anything you like".

Rust note · slice patterns and let-chains

if let [format] = available_formats matches only when the slice has exactly one element, and names it format. The && after it chains another condition onto the same if let, which is new in Rust's 2024 edition. The rest is an iterator chain: copied() turns references into values, find returns an Option, or_else supplies a fallback Option, and ok_or turns None into an error.

Coming from OpenGL

The UNORM part matters. An _SRGB swapchain format would make the GPU convert linear colour to sRGB as it writes, as GL_FRAMEBUFFER_SRGB did. A UNORM format stores shader output unchanged. RustyVulkan's textures are also loaded as UNORM (Chapter 5), so colours pass from texture to screen without conversion, and lighting is computed on gamma-encoded values. (The SRGB_NONLINEAR colour space only tells the display how to interpret the stored numbers.) That's a common simplification, and it's how many OpenGL renderers worked too.

Present mode and size

Most platforms, macOS included, report the surface's current_extent, and the swapchain must match it. On some platforms the special value u32::MAX means the application decides, in which case the window's inner_size() (in physical pixels) is clamped into the allowed range.

Creating the swapchain

Fields worth knowing:

  • image_usage: COLOR_ATTACHMENT: these images will be rendered into. This renderer never samples them as textures or copies to them.
  • image_sharing_mode: EXCLUSIVE: only one queue family touches them, which is true here, since one queue does everything (Chapter 3).
  • pre_transform and composite_alpha: keep the surface's current orientation, and treat the window as opaque if that's allowed. choose_composite_alpha walks a preference list and returns the first mode the surface supports.
  • clipped: TRUE: the driver may skip pixels hidden behind other windows.
  • old_swapchain: null the first time. On a resize it's the swapchain being replaced, which lets the driver reuse or retire the old images without a gap on screen (see "If recreation fails" below).

Recording ownership as it goes

After the swapchain itself come the per-image views and the two multisampled images. Any of those steps can fail, and a failure must not leak what came before. DEVELOPMENT.md names this constructor as the example of the pattern from Chapter 2:

The Swapchain struct is created first, with null handles and None allocations. Each step then stores its result in the struct the moment it succeeds. If any step fails, the struct accurately lists what exists, and cleanup destroys exactly that.

Rust note · a closure as a "try block"

(|| -> Result<(), Box<dyn Error>> { … })() defines a closure and calls it immediately. Its only purpose is to give ? somewhere to return to. A failing step exits the closure, not the whole function, so the code after it gets the chance to clean up before passing the error on.

Two new terms appear here. An image view describes how to interpret an image: which format, which parts (colour or depth), and which sub-images (the smaller mipmap levels, or layers of an image array). Vulkan always reads and writes images through views. create_image_views makes one per swapchain image, and its error path destroys any already made. The TRANSIENT_ATTACHMENT usage on the multisampled images tells the driver their contents only matter during rendering and never need to be read back afterwards, which some GPUs can exploit to save memory traffic.

Tearing down, safely and repeatably

cleanup is written so that running it twice is harmless. drain(..) empties the vector of views as it goes. Option::take removes each allocation (Chapter 2). std::mem::replace swaps each handle for null and hands back the old value to destroy, so a second run would only "destroy" null handles, which Vulkan permits. Note that the swapchain's own images aren't destroyed: they belong to the swapchain and go with it.

Wait for the GPU to stop using the old images, build the new swapchain with the old one as old_swapchain, destroy the old resources, and overwrite self with the new value. VulkanBase::recreate_swapchain then rebuilds everything sized per swapchain image, including command buffers, semaphores, uniform buffers and their descriptor sets, and the timestamp pool (Chapter 9). If the pixel format changed, it also marks every pipeline for rebuilding (Chapter 7).

If recreation fails

Vulkan retires the old swapchain as soon as replacement is attempted. If creating the new one fails, the old Rust value is kept only so it can still be cleaned up; it must not be rendered with. The error propagates out and the application exits, a deliberate policy that DEVELOPMENT.md explains (Chapter 16).

Recap

  • The surface is the window as Vulkan sees it, created through ash-window from the window's raw handles. On macOS it wraps a Metal layer.
  • The swapchain is a ring of images you acquire, render into and present. Here there are three, in B8G8R8A8_UNORM, using mailbox presentation if available and FIFO otherwise.
  • Multisampled colour and depth images live alongside it, because they share its size.
  • Construction records ownership step by step so a failure cleans up exactly what was made. cleanup is safe to repeat.
  • Resizes, and out-of-date or suboptimal results, request recreation, which is applied once at the start of a frame. Zero-sized windows are skipped.
