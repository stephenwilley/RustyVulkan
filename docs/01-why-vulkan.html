Overview The big picture

There is a lot to set up before Vulkan draws anything. If you remember getting an OpenGL triangle on screen in fifty lines, a Vulkan version running to hundreds or even a thousand can feel like a wall. That upfront boilerplate is real: devices, memory, drawing state and synchronisation all need decisions that OpenGL made for you. This chapter starts with the setup, and the next chapters give those decisions meaning. You can follow the overviews first, then return to the source when you want the details.

If your OpenGL memories start with glBegin

The familiar triangle is still vertices transformed into a picture. The way you supply it has changed: vertex buffers replace streams of glVertex calls; your code builds the matrices that once lived on OpenGL's matrix stacks; and small GPU programs called shaders do the transformation and lighting that glLight and the fixed-function pipeline supplied. GLSL, their C-like language, gets a refresher in Chapter 6. You don't need to know VAOs, uniform buffers or instancing yet; the comparisons explain them where they appear.

OpenGL did a lot behind your back

OpenGL was designed in the early 1990s around a simple idea: the programmer sets some state ("this texture is bound, blending is on, use this shader") and then says "draw". The driver, the GPU vendor's software that sits between your program and the hardware, did everything else. It decided where in memory your textures lived. It checked every call for mistakes. It compiled your shaders. It worked out when it was safe to overwrite a buffer the GPU might still be reading. And it quietly waited, or copied, whenever it wasn't sure.

That made OpenGL approachable, but the driver had to guess what you'd do next, so a harmless-looking state change could cause a hidden stall or a shader recompile, and every vendor guessed differently. And because all that state lived in one global "context", using several CPU threads was awkward at best.

Vulkan makes you say it out loud

Vulkan, released by the Khronos Group in 2016 as OpenGL's successor, turns the deal around. The driver stops guessing. Instead, you tell it, explicitly and up front:

  • which GPU you want and what features you'll use;
  • exactly how memory is allocated and what each piece is for;
  • all the drawing state for a given kind of draw, baked into one object ahead of time;
  • the commands to run, recorded into lists that you hand to the GPU yourself;
  • when one piece of work must wait for another.

The result is famously verbose (a first triangle takes hundreds of lines), but the driver becomes thin and more predictable: more costs and dependencies are explicit, although the driver and operating system still affect performance. Much of this codebase is that explicit setup, and this guide is about reading it.

A few words you'll meet everywhere

Each of these gets its own chapter. For now, a one-line feel for them is enough:

  • Instance: your program's connection to the Vulkan system.
  • Device: one GPU, opened for use. You create almost everything from it.
  • Queue: the inbox where you post work for the GPU.
  • Command buffer: a recorded list of GPU commands ("draw this, then copy that").
  • Pipeline: one object holding all the drawing state for a kind of draw, shaders included.
  • Swapchain: the small set of images that take turns being shown in the window.
  • Fence and semaphore: signals that make the CPU, or the GPU, wait until some earlier GPU work has finished.
  • Pass: one stage of drawing a frame that renders into a particular set of images. This renderer has three: shadows, the main scene, and the UI on top.

Because Vulkan trusts you, mistakes aren't caught for you by default. During development you switch on validation layers: an optional checking layer that reports misuse as it happens. This project turns them on automatically in debug builds.

How this project is layered

RustyVulkan is written in Rust. Vulkan is a C API, so the project reaches it through ash, a thin Rust wrapper whose functions map almost one-to-one onto Vulkan's C functions. Below that, the stack depends on the operating system. Apple doesn't ship Vulkan; macOS's native GPU API is Metal. So on a Mac this project uses KosmicKrisp, a Vulkan driver that is implemented on top of Metal and ships with LunarG's macOS Vulkan SDK. The project targets Vulkan 1.3 and, per its README, needs an Apple Silicon Mac on macOS 26 or newer (KosmicKrisp requires Metal 4), the Vulkan SDK, and the Assimp model library from Homebrew.

Rust note · modules

C has no module system; a program is just a pile of .c files that the linker stitches together, with headers to share declarations. In Rust, mod app; says "there is a module called app; find it in app.rs or app/mod.rs". Each folder's mod.rs then lists its own children (src/app/mod.rs, src/vulkan/mod.rs, src/graphics/mod.rs). The result is a tree, and there are no headers.

So mod is what makes a file part of the build. use app::app::App; only shortens a name: the path reads "module app, its child module app, the type App", and afterwards you can just write App. Items are private to their module unless marked pub. You'll also see pub(super), which means "visible to the parent module and everything inside it".

Rust note · conditional compilation

#[cfg(target_os = "macos")] is an attribute. It plays the role of #ifdef __APPLE__, but it attaches to a single item (a function, a use line, a struct field, a statement) rather than to an arbitrary span of text. Above, PathBuf is only imported on macOS because only the macOS code uses it. The codebase uses #[cfg(debug_assertions)] the same way to switch on Vulkan's validation layers in debug builds only (Chapter 3).

main: configure, then run

configure_runtime fixes up the process environment, then App::new().run() runs the application until the window closes. If either fails, the error is printed and the process exits with a failure status.

Rust note · errors are values

Rust has no exceptions. A function that can fail returns Result<T, E>: either Ok(value) or Err(error). if let Err(e) = … is a pattern match that runs its block only when the result is an error. The ? operator you'll see on almost every Vulkan call means "if this is an error, return it to my caller right now". The full story is in Chapter 2.

Optional · macOS startup details

The rest of this walkthrough explains how the app finds its assets and Vulkan driver on macOS. On a first reading, you can skip to Chapter 2 for the Rust foundations and return here when you're curious about startup or packaging.

Finding the assets when launched from Finder

The renderer loads models and textures by relative paths under assets/. That works under cargo run, which starts the program in the repository folder. When the app is double-clicked in Finder, though, the working directory is meaningless. So configure_runtime checks whether the executable lives inside a macOS app bundle (Something.app/Contents/MacOS/) and, if so, moves the working directory to the bundle's Contents/Resources, where the packaging script copies the assets (Chapter 16). Shaders are compiled during the build and embedded in the executable.

Rust note · Option, and chaining on it

Rust references cannot be null; raw pointers used at the C boundary can be. A value that might be absent normally has type Option<T>, which is either Some(value) or None, and the compiler won't let you use the value without handling the None case.

The let bundle_resources = … statement is a chain of small steps on an Option. Read them as a pipeline that stops at the first None: take the executable's folder (parent()); then that folder's parent (and_then); keep it only if it's named Contents (filter); then turn it into …/Contents/Resources (map). The |x| … syntax is a closure, an inline anonymous function. In C this would be four nested ifs with null checks.

if let Some(resources) = &bundle_resources then runs only when the chain produced a value. The & borrows it rather than consuming it, because it's used again on the next line (borrowing is covered in Chapter 2). On the last line, as_deref() turns that borrowed Option<PathBuf> (an owned path) into an Option<&Path> (a borrowed view of one), which is what the next function asks for.

Choosing the Vulkan driver on macOS

A machine can have several Vulkan drivers installed. The Vulkan loader, the library that ash links to, discovers them through small JSON ICD manifests (ICD stands for "installable client driver"), each pointing at a driver library. The environment variable VK_DRIVER_FILES overrides discovery and names the manifest to use. RustyVulkan sets it to KosmicKrisp's manifest, unless you've already set it yourself for testing.

The search order is: the app bundle; otherwise the SDK named by $VULKAN_SDK; otherwise the SDK's system-wide install under /usr/local. If none exists, it fails early with instructions rather than letting Vulkan fail mysteriously later.

.find(…) returns the first candidate that is a real file, as an Option; .ok_or_else(…) turns a None into an error so ? can return it.

Rust note · why is set_var unsafe?

Changing environment variables isn't thread-safe at the C library level: if another thread reads the environment at the same moment, the program can crash. Since the 2024 edition of Rust (which this project uses), std::env::set_var is therefore marked unsafe. Calling it requires an unsafe { … } block, which is the programmer's signed promise that the rules the compiler can't check are being followed. The comment above it gives the justification: this runs before any other threads exist. You'll see this habit throughout the codebase: an unsafe block, with a comment saying why it's sound; Chapter 2 explains why nearly every Vulkan call is unsafe.

Coming from OpenGL

In OpenGL you never chose a driver; the windowing system handed you a context. Vulkan's loader-and-ICD design makes the choice explicit and lets several drivers coexist, which is how a Vulkan-on-Metal driver can be dropped onto a Mac at all. (Apple deprecated OpenGL in 2018; its version stops at 4.1.)

What happens next

App::new().run() creates a winit event loop. When the operating system says the app is ready, it opens the window, builds the whole Vulkan backend (VulkanBase::new), loads the scene, and registers the shadow and main passes, plus a UI pass that can be toggled on and off. Then it draws a frame whenever winit asks. The rest of this guide follows that path roughly in order.

Recap

  • OpenGL's driver hid memory, validation, compilation and synchronisation. Vulkan hands all of that to you in exchange for predictable performance and room for multithreading.
  • RustyVulkan reaches Vulkan through ash. On macOS, Vulkan itself is provided by KosmicKrisp, a driver built on Metal, selected through the loader's VK_DRIVER_FILES variable.
  • Each frame: wait, acquire an image, record shadow, main and UI passes, submit, present, advance.
  • main.rs fixes the working directory for app bundles and picks the driver before any threads start, then hands everything to App.
