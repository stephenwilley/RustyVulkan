Instance, devices and queues

Before anything can be drawn, the program has to connect to Vulkan, look at the GPUs on the machine, pick one, switch on the features it needs, and get a queue to send work to.

Overview Source walkthrough Recap

Overview The big picture

In OpenGL, asking the window system for a context gave you everything at once: a GPU chosen for you, all its features on, and an implicit place to send commands. Vulkan splits that single step into several explicit ones, each a decision you make.

The instance, layers and extensions

The instance is the program's connection to Vulkan. Creating it is where you declare which version of the API you're written against (1.3 here), and what optional extras you want:

  • Layers sit between your program and the driver, intercepting every call. The important one is the validation layer, Khronos's checker for Vulkan's usage rules. With it on, mistakes that would otherwise be silent produce a readable message. It costs speed, so this project enables it only in debug builds.
  • Extensions add functionality beyond the core API. Some belong to the instance (talking to the window system, receiving debug messages); others belong to a device (the swapchain, for showing images on screen).

Physical and logical devices

A physical device is a GPU as Vulkan reports it: its name, its type (built-in or discrete), its limits, and what optional features it supports. You can ask questions of it, but you can't use it yet. A logical device is what you create from it: your own session with that GPU, with exactly the features and extensions you asked for switched on. Nearly every other Vulkan object is created from the logical device, and it's what the codebase means whenever it says device.

RustyVulkan's choice is simple: prefer a discrete graphics card, but only if it can do everything the renderer needs. On an Apple Silicon Mac there is only one GPU, so the question is really "does this one qualify?".

Queues and queue families

Work reaches the GPU through queues. A GPU groups its queues into families by what they can do: graphics, compute, data transfer. Whether a family can show images in a particular window ("present to a surface") is a separate question that depends on the window. That's why the window's surface is created before the GPU is chosen. This renderer looks for one family that can both draw and present, and uses a single queue from it for everything.

Deeper dive

All of this happens in VulkanBase::new in src/vulkan/base/setup.rs, which builds the whole backend in one long function. It reads top to bottom in the order of the diagram. (Patterns from Chapter 2 aren't re-explained.)

Checking for the validation layer

Entry::linked() gives the function table for the loader linked in at build time. Then, in a debug build, the code asks the loader which layers are installed. If the validation layer is missing, it fails with a clear message rather than silently running unchecked (so debug runs need the layer installed, as DEVELOPMENT.md says). Every item marked #[cfg(debug_assertions)], even the bare { … } block, is compiled only into debug builds (Chapter 1). In a release build the layer list is simply empty.

Rust note · C strings

Rust's own strings (String, &str) store a length and are not zero-terminated, so they can't be handed to C directly. c"…" is a C string literal: a zero-terminated string of type &CStr. CStr::from_ptr goes the other way, wrapping a const char* from Vulkan so it can be compared. CString is the owned version, used when building one at run time. The type *const i8 is Rust's spelling of const char*; a Vec of them is the const char* const* array Vulkan wants for name lists.

Creating the instance

create_instance starts by describing the application and collecting the instance extensions it needs:

enumerate_required_extensions comes from the ash-window crate. It asks the windowing system which surface extensions this platform needs (on macOS, the generic surface extension plus a Metal-specific one), so the code never names them. In debug builds it adds VK_EXT_debug_utils, which lets the validation layer report back to us.

Then comes a small piece of driver diplomacy:

Some Vulkan implementations, MoltenVK being the best known, run on top of another API and can't support every part of the specification. Vulkan calls these portability drivers. To stop programs accidentally using one, the loader hides them unless the instance opts in with this flag and extension. KosmicKrisp doesn't need it, but rather than hard-coding a driver, the code opts in whenever the loader offers the extension. After that, the create call shown in Chapter 2 makes the instance.

Hearing from the validation layer

With the debug extension enabled, the code registers a debug messenger: a callback that the validation layer calls whenever it has something to say.

The callback itself just formats the message and prints it to standard error. Returning vk::FALSE tells the layer not to abort the Vulkan call that triggered the message:

Rust note · a function C can call

extern "system" tells the compiler to use the platform's C calling convention, so that Vulkan (C code) can call this Rust function through a pointer. Its parameters are raw C types: a raw pointer *const to a struct, and a *mut c_void (C's void*), unused here. Reading through raw pointers is one of the operations that needs unsafe. pfn_user_callback: Some(vulkan_debug_callback) stores the function pointer in an Option, because a C function pointer may be null and Rust models "maybe null" that way.

Coming from OpenGL

This is the Vulkan cousin of glDebugMessageCallback from OpenGL 4.3. The difference is that OpenGL drivers usually did their own (cheap, partial) checking all the time, while Vulkan drivers check almost nothing. The validation layer is where nearly all the checking lives, and you choose when to pay for it.

Choosing a GPU

The window surface is created next (Chapter 4), because presentation support is needed to judge GPUs. Then choose_device_and_queue_family tries each GPU, first looking only at discrete ones and then at everything else:

For each candidate, it applies four tests in turn and moves to the next GPU (continue) on the first failure:

  1. Can it hold this renderer's per-draw data? The scene and grass use 144 bytes of push constants (Chapter 7). Vulkan 1.3 guarantees only 128, so the device's reported limit must be checked. A GPU below 144 is skipped with a diagnostic before any pipeline is created.
  2. Does it have the required device extensions? REQUIRED_DEVICE_EXTENSIONS lists them: the swapchain extension, without which there's nothing to display; VK_KHR_push_descriptor, which lets draws write texture descriptors straight into the command buffer (Chapter 8); and VK_KHR_maintenance5, which lets pipelines take SPIR-V directly (Chapter 6).
  3. Does it support the features this renderer uses? It draws with dynamic rendering (Chapter 7) and records its barriers with the clearer synchronization2 commands (Chapter 10), both Vulkan 1.3 features. An extension can also come with features of its own that must be checked separately, as maintenance5 does. The GPU must report Vulkan 1.3, and then report all three features as supported, using the push_next query shown in Chapter 2.
  4. Is there a queue family that can both draw and present to our surface? The first one found wins, and the function returns the GPU and that family's index together.

has_extension is a closure that captures the GPU's extension list, and .iter().all(…) asks it about each required name in turn.

Once a GPU is chosen, new records a few of its capabilities for later:

The supported multisample counts for colour and depth are intersected, giving the anti-aliasing options the UI can offer (Chapter 10). Multi-draw indirect, which lets one command issue many draws, and indirect "first instance", which lets those commands pick out a range of instances, are both used by the grass if available (Chapter 14). The & between two flag sets is a bitwise AND, just as in C.

Opening the logical device

create_logical_device_and_queue asks for exactly what the renderer uses and nothing more:

Reading it in order:

  • Features. Multi-draw indirect, indirect first-instance and non-solid fill mode (for wireframe) are requested only when supported. Enabling only what's used keeps device creation working on implementations that lack the rest.
  • Queues. One queue from the chosen family. Every queue needs a priority between 0 and 1, passed as a pointer to an array; queue_priority is that array, kept in a local variable so the pointer stays valid until create_device returns.
  • Extensions. Built just above (elided): the required device extensions, plus VK_KHR_portability_subset if listed. A portability driver uses that one to declare which features it can't provide, and Vulkan requires you to enable it when it's present.
  • Features, switched on. Supporting a feature isn't enough; it must be enabled. Dynamic rendering and synchronization2 are both turned on in one PhysicalDeviceVulkan13Features struct, and maintenance5 in its own struct. Both are chained onto the create info with push_next, after a struct literal sets the other fields.
  • The queue. get_device_queue doesn't create anything. Queues are made with the device; this just fetches the handle of queue 0 in our family.

What else new sets up

After the device, VulkanBase::new carries on creating the objects the rest of the guide is about. In order: a pipeline cache shared by all pipelines (Chapter 7); a command pool (Chapter 9); the VMA memory allocator (Chapter 5); the global descriptor layout (Chapter 8); the swapchain (Chapter 4); uniform buffers, descriptor sets and the shadow sampler; per-frame fences and semaphores and the command buffers (Chapter 9); and a timestamp query pool used to measure GPU time per pass, which is where the "GPU: 11.05 ms" in the screenshot's menu bar comes from. Everything ends up as a field of the VulkanBase struct, which is the single owner from Chapter 2.

Recap

  • The instance declares the API version (1.3), layers and instance extensions. Validation is on in debug builds and reports through a debug-messenger callback.
  • Portability enumeration is enabled whenever the loader offers it, so portability drivers stay usable; KosmicKrisp doesn't need it.
  • A GPU qualifies if it supports Vulkan 1.3 with dynamic rendering and synchronization2, the swapchain, push-descriptor and maintenance5 extensions (with the maintenance5 feature), and a queue family that can draw and present to the window's surface, plus at least 144 bytes of push constants. A discrete GPU is preferred. Wireframe is optional: supported devices enable non-solid fill mode, while others keep the UI toggle disabled. It is currently unavailable with KosmicKrisp, pending driver implementation of fillModeNonSolid.
  • The logical device enables only the features the renderer uses, and provides the single queue used for all work.
