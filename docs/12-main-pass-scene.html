The main pass and the scene

What the scene is made of, how models get into it, how the camera turns it into a picture, and the loop that draws it all each frame.

Overview Source walkthrough Recap

Overview The big picture

A scene is a list of lightweight references

Everything drawn by the main pass's ordinary draw loop is a scene object: a position, rotation and size in the world, plus one or more parts. Each part names a mesh and a material by number, with its own small offset. The actual GPU resources (vertex buffers, textures, pipelines) live in two managers, which hand out those numbers and make sure nothing is loaded twice (Chapter 8). So the forty-eight rocks, drawn from five rock models, cost five sets of buffers, not forty-eight.

The scene in the screenshot is built once at start-up:

  • a generated terrain mesh for the valley (Chapter 13);
  • the hut (a .glb model) and the marble sphere (a .gltf model), loaded with Assimp, a widely used model-loading library;
  • two textured test cubes;
  • clusters of rocks, made from five imported rock models;
  • a large, flat debug grid, shown (without grass) only when the terrain is switched off in the UI.

The sky and the grass are drawn by their own specialised renderers inside the same pass (Chapters 13 and 14).

The camera

The camera is two matrices. The view matrix says where the eye is and which way it looks, re-expressing the world relative to the eye. The projection matrix is the lens: a 45° field of view, with nothing drawn nearer than 0.5 m or further than 220 m (the terrain is 200 m across). It's a first-person camera: WASD walks over the ground, the mouse looks around, and the eye stays 1.8 m above the terrain.

Vulkan disagrees with OpenGL on two conventions, so the projection is corrected for both. In Vulkan's clip space, Y points down, and depth runs from 0 to 1 rather than −1 to 1.

One frame of the main pass

After clearing, the pass draws the sky first. It doesn't touch the depth buffer, so everything else paints over it. Then it walks the scene: for each visible object and each part, it switches pipeline and textures if the material changed, sends that part's matrices as push constants (a small block of per-draw data recorded straight into the command buffer), and draws its mesh. Finally the grass is drawn, and rendering ends with the anti-aliasing resolve (Chapter 10).

Deeper dive

Transforms, parts and objects

A transform is translate × rotate × scale, with a quaternion for rotation and a single uniform scale. The uniform scale is a deliberate restriction: the shaders transform normals with the plain model-view matrix, which is only correct without stretching (Chapter 6).

Both types derive Clone, and ScenePart is even Copy, because all it holds is two indices and a transform. Cloning a rock's parts to place another copy of it costs a few bytes.

The camera's matrices

cgmath's perspective builds an OpenGL-style matrix. Negating proj.y.y flips Y so the image comes out upright under Vulkan's Y-down convention. Without it, the mirror image would also reverse triangle winding; with it, OpenGL's counter-clockwise front faces stay counter-clockwise (Chapter 7). The fixed matrix then halves Z and adds half, mapping depth from −1..1 to 0..1. The shadow cascades reuse that depth fix-up but not the flip (Chapter 11). The view matrix is a standard right-handed look-at, built from yaw and pitch angles in set_view_yaw_pitch.

Coming from OpenGL

OpenGL code can't simply be pointed at Vulkan: unchanged, everything renders upside down, and anything in the nearer half of OpenGL's depth range is clipped away. The alternative to flipping the projection is a negative-height viewport (allowed since Vulkan 1.1), which has the same effect on the image and on winding.

Rust note · items inside functions

OPENGL_TO_VULKAN_MATRIX is declared as a const inside the function body. Rust lets you place constants, functions and even structs inside a function to keep them local; they behave exactly like their top-level versions. The loader below does the same with a fn decompose.

Pushing per-object matrices

For each part, the main pass computes model-view and model-view-projection matrices and packs them, with the material's UV tiling, into the 144-byte push-constant block of Chapter 7:

ScenePushConstants names the two matrices and the padded UV field. cgmath already stores matrix columns, so conversion to [[f32; 4]; 4] preserves GLSL's column-major order. bytemuck::bytes_of borrows the struct's bytes for the Vulkan command; no heap allocation or manual byte offsets are needed.

Rust note · a checked GPU layout

#[repr(C)] fixes field order. Deriving Pod verifies there is no hidden padding or invalid byte representation. Explicit padding is initialized along with every field. Compile-time assertions in gpu_data.rs check the sizes and offsets expected by GLSL: matrices at 0 and 64 bytes, the final vector at 128, and 144 bytes in total.

The draw loop

Objects are drawn in scene order, not sorted, and the pipeline and descriptors are rebound only when a part's material differs from the previous part's (the binding itself was shown in Chapter 8). Consecutive parts sharing a material therefore cost one push and one draw each; the rocks alternate between two materials, so they rebind more often. record binds the mesh's vertex and index buffers and issues cmd_draw_indexed.

Loading models with Assimp

import.rs is a one-line front door to assimp_loader.rs, which uses the russimp-ng bindings to the Assimp C++ library:

Assimp turns every polygon into triangles, computes the tangent and bitangent vectors that normal mapping needs, and reorders vertices for the GPU's cache. The loader then works through the file in three steps.

Materials. For each material it looks for a colour texture and a normal map, resolving file names relative to the model's folder, and chooses shaders accordingly:

Textured materials use main.vert/main.frag. Untextured ones use the vertex_color pair, which lights a colour carried in each vertex. The loader copies the material's base colour into every vertex for exactly that reason.

Meshes. Each Assimp mesh becomes a CPU Mesh, with safe defaults for missing normals, UVs or tangents, and is uploaded through the mesh manager, which reuses it if the name has been seen before:

Nodes. A model file is a tree of nodes, each with a transform and some meshes. The loader walks the tree with an explicit stack, combining transforms on the way down, and emits one part per mesh with its transform relative to the root. Building the scene

App::set_up_scene requests materials and meshes, loads models, places everything on the terrain, and adds it all to the scene. Each object is stood on the ground using the terrain's height function and the lowest point of its mesh's bounding box, which the mesh manager keeps after the CPU vertices are discarded. The debug grid

The infinite grid's vertex shader (infinite_plane.vert) takes a 2 × 2 unit plane and stretches it to two kilometres, centred under the camera (though the 220 m far plane clips it). Its fragment shader (infinite_plane.frag) draws grid lines from fwidth, the screen-space rate of change, so they stay one pixel wide at any distance, and fades them with distance. It's drawn late, with blending on and depth writes off, and the render graph swaps it with the terrain each frame according to the UI's ground toggle.

Recap

  • A scene object is a transform plus parts. Parts refer to manager-owned meshes and materials by index, so reuse is nearly free.
  • The camera's projection flips Y and remaps depth to 0..1 for Vulkan. The view is a first-person look-at, kept 1.8 m above the terrain.
  • The main pass draws the sky, then each part (rebinding only when the material changes, pushing 144 bytes of matrices), then the grass.
  • Assimp loads glTF/GLB, triangulating and generating tangents. Materials get textured or vertex-colour shaders, and node transforms are flattened to uniform-scale parts.
