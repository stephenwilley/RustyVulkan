GPU memory

Buffers and images, the different kinds of memory behind them, and the two ways this renderer gets data from the CPU onto the GPU.

Overview Source walkthrough Recap

Overview The big picture

Two kinds of resource

Everything the GPU reads or writes lives in one of two kinds of object:

  • A buffer is a plain run of bytes: vertex data, triangle indices, a block of per-frame settings such as light directions.
  • An image is structured pixel data: a texture, a depth map, a render target. Images have a size, a pixel format and a sample count, and are usually stored in a GPU-specific tiled arrangement that makes nearby pixels fast to fetch together. The CPU can't easily write that arrangement directly.

Creating either one gives you only a description. It has no memory yet. In Vulkan, you allocate memory separately and attach it, and that's where the choices come in.

Memory types

A GPU offers several memory types with different trade-offs. The two properties that matter most are:

  • Device-local: fastest for the GPU. On a PC graphics card this is the card's own memory, which the CPU often can't see at all.
  • Host-visible: the CPU can map it, getting an ordinary pointer to write through. It can be system memory or CPU-accessible device-local memory; performance depends on which memory type the driver exposes.

These are independent properties: a memory type can be both device-local and host-visible, even on a discrete graphics card.

On Apple Silicon the CPU and GPU share the same physical memory (unified memory), so the distinction is far smaller. Vulkan code is still written to handle both, which is why the code states a preference for each allocation rather than assuming.

Allocating Vulkan memory directly is laborious. You must search the memory types yourself, and drivers limit how many separate allocations you may make (to about four thousand on many drivers), so real programs carve many resources out of a few big blocks. RustyVulkan uses VMA, AMD's widely used Vulkan Memory Allocator, which does both jobs. You say "a buffer this big, used like this, preferably CPU-writable", and VMA picks the memory type and sub-allocates it.

Two ways to upload

This renderer gets data onto the GPU in one of two ways, depending on what the data is.

Write it in place. Vertex and index buffers, and the per-frame settings, are put in host-visible memory. The CPU maps it, copies the bytes in, and the GPU reads from there. That's simple, and on unified memory it costs little.

Stage it. Textures (and the grass's large instance buffers, Chapter 14) go into device-local memory. Textures in particular are images with an optimal tiled layout, which the CPU can't write. So the pixels are first copied into a temporary host-visible staging buffer, and then the GPU itself is told to copy from that buffer into the image, rearranging the pixels as it goes. The staging buffer has to stay alive until the GPU has actually done that copy.

The bottom row introduces an idea that recurs throughout Vulkan. An image's layout is the arrangement its data is in, and each kind of use expects a particular one. Moving an image from one layout to another is an explicit step, recorded with a barrier, which also makes sure the previous step has finished. Chapter 10 covers barriers properly.

Rust note · repr(C), derive, and bytemuck

By default, Rust may reorder a struct's fields to save space. #[repr(C)] forbids that: fields are laid out in declaration order with C's padding rules, so the GPU can be told exactly where each one is. Here that's six arrays of f32, 68 bytes per vertex.

#[derive(…)] asks the compiler to generate standard trait implementations. Clone, Copy make the type copyable like an integer (Chapter 2), and Default gives an all-zero value. Pod and Zeroable come from the bytemuck crate. Pod ("plain old data") is a checked promise that the type has no padding, pointers or other hidden state, so viewing it as raw bytes is safe. The derive fails to compile if that isn't true.

The same file also describes this layout to Vulkan, field by field, with offset_of!(Vertex, normal) giving each field's byte offset. That description is part of the pipeline, so it's covered in Chapter 7.

Vertex and index buffers: write in place

Step by step:

  • The buffer is described: its size in bytes, and that it'll be used as a vertex buffer.
  • VMA is asked for memory: AutoPreferHost picks CPU-visible memory where possible, and HOST_ACCESS_SEQUENTIAL_WRITE promises that the CPU will only write it, in order. That lets VMA choose memory that's fast to write but slow to read back. create_buffer creates the buffer, allocates memory and binds them together, returning both.
  • The memory is mapped, the data copied with copy_nonoverlapping (Rust's memcpy, except that it counts elements of type T, not bytes), then flushed and unmapped. Asking for MAPPED as well as mapping by hand is redundant but harmless.

The flush matters. Some host-visible memory is non-coherent: the CPU's writes may sit in its caches, invisible to the GPU, until explicitly flushed. VMA's flush does nothing on coherent memory, so calling it unconditionally is the portable choice. (Apple Silicon's memory is coherent, so here the flush is effectively free.) DEVELOPMENT.md makes it a rule: flush non-coherent host writes before submission.

Rust note · generics

new<T: Pod>(…, data: &[T]) is a generic function: it works for a slice of any type T, provided T implements Pod. The grass code uses the same trick in its own upload_buffer<T: Pod> (Chapter 14). The compiler generates a separate copy for each type used (monomorphisation), so there's no run-time cost. &[T] is a slice, a pointer plus a length, and size_of_val gives its total size in bytes.

IndexBuffer::new is the same with u32 indices and INDEX_BUFFER usage. LoadedMesh::load creates one of each for a mesh, keeping the mesh's bounding box for placing it on the terrain later.

Coming from OpenGL

This is roughly glGenBuffers + glBufferData made explicit (though GL would likely have put static mesh data in GPU-only memory). In GL the usage hint was a guess the driver might ignore, and where the bytes went was invisible. Here the code states exactly which memory it wants, and does the copy itself.

It has one mip level only: this renderer doesn't generate smaller mipmap versions of its textures. And it's R8G8B8A8_UNORM, the format behind Chapter 4's note about gamma.

Each barrier carries its own pair of pipeline stages: "work at the source stage must finish before work at the destination stage may start". The first has no source stage, since nothing has touched the new image yet, but the copy may not start until the layout change is done. The second makes fragment shaders wait for the copy to complete. These are synchronization2 barriers, explained in Chapter 10.

Coming from OpenGL

glTexImage2D did all of this invisibly: it copied your pixels somewhere, scheduled an upload, tracked when it was safe to reuse your memory, and converted to the GPU's tiling. Pixel buffer objects were OpenGL's opt-in version of a staging buffer.

Not finished yet

DEVELOPMENT.md lists texture uploads among the paths that still lack full partial-failure cleanup. For example, if create_image or create_image_view fails in upload, the staging buffer (and in the second case the image) hasn't yet been handed to anyone, so nothing will destroy it. The same applies in LoadedMesh::load if the index buffer fails after the vertex buffer succeeded. Compare the swapchain's step-by-step ownership in Chapter 4.

Recap

  • Buffers are raw bytes; images are tiled pixel data with a format and layout. Neither has memory until you allocate and bind it.
  • VMA picks memory types from stated preferences and sub-allocates from large blocks.
  • Vertex, index and per-frame uniform data are written in place into host-visible memory, then flushed.
  • Textures go through a staging buffer: CPU copy, then a recorded GPU copy bracketed by layout barriers. Staging memory lives until a fence says the GPU is done.
