The ImGui overlay

How the menus, sliders and debug windows in the screenshot are described each frame by Dear ImGui, and how the renderer turns that description into Vulkan draws on top of the scene.

Overview Source walkthrough Recap

Overview The big picture

Immediate-mode UI

The panels in the screenshot (the menu bar with its CPU and GPU timings, the "Sun Light" sliders, the "Shadow Cascades" window) come from Dear ImGui, a popular C++ UI library used here through the imgui Rust crate. It's an immediate-mode UI: there are no button or window objects kept around. Every frame, the code simply runs through the interface again, "a window called Sun Light, containing a slider for X direction…", and ImGui works out layout, input and state as it goes.

ImGui never draws anything itself. At the end of the frame it hands back draw data: lists of plain 2-D triangles (positions, texture coordinates and colours), grouped into commands that each say which texture to use and which rectangle to clip to. Turning that into pixels is the application's job, and that's what ImGuiRenderer does.

Drawing it with Vulkan

The UI is drawn last, in its own pass, recorded into the same command buffer straight onto the finished scene in the swapchain image (Chapter 10). The renderer needs a handful of things:

  • a texture holding every letter of the font, built by ImGui once and uploaded at start-up;
  • vertex and index buffers that are refilled every frame, because the UI's triangles change every frame;
  • a simple pipeline: 2-D, no depth test, standard alpha blending;
  • a scissor rectangle per command, so text in a window can't spill outside it.

The same machinery can show any GPU image in a window. That's how the four shadow-map cascades (Chapter 11) appear as greyscale pictures in the "Shadow Cascades" panel.

Deeper dive

Describing the UI

UiPass::execute starts an ImGui frame (the winit support crate passes in mouse, keyboard and window size) and builds the interface:

menu_item returns true on the frame it's clicked, so the UI code reacts in the same place it's declared. The values handed to sliders are fields of the app's world controls, which the render graph copies into the uniform buffer each frame (Chapter 9), so dragging the "Sun Light" sliders moves the sun on the very next frame.

Rust note · guards that end things

begin_menu returns an Option holding a token. While the token exists, the menu is open; _main_menu.end() closes it, and if you forget, the token's Drop closes it anyway when it goes out of scope. That's the RAII idea from Chapter 2 applied to a UI's begin/end pairs, which in C++ ImGui are easy to mismatch.

The pipeline

ImGui's vertex is 20 bytes: a 2-D position, a texture coordinate, and a colour packed as four bytes. The colour uses R8G8B8A8_UNORM, so the GPU unpacks it to four floats for the shader, as the grass did with 16-bit values (Chapter 14):

The rest is the simplest pipeline in the project: no culling, no depth test, a single sample (the UI draws after the anti-aliasing resolve), no depth attachment format at all, and "over" blending:

The only per-draw data is a projection matrix, sent as a 64-byte push constant to the vertex shader. ImGui works in window coordinates (pixels from the top-left corner), and this matrix maps them to Vulkan's −1..1 clip space. Because Vulkan's Y already points down, like screen pixels, no flip is needed:

bytemuck::cast_slice views the 4 × 4 array of floats as bytes without copying, the safe reinterpretation that Pod types allow (Chapter 5). The shaders are tiny: the vertex shader, imgui.vert, applies the matrix, and the fragment shader multiplies the vertex colour by the texture.

Copying the red channel into all three colour channels shows a one-channel image, like a depth map, as grey. That's harmless for the font, whose texture is white with the shapes in its alpha channel.

Uploading the font

ImGuiRenderer::new, in imgui_renderer/resources.rs, asks ImGui for its font atlas as RGBA pixels and uploads it exactly as textures were uploaded in Chapter 5: staging buffer, device-local image, a barrier-copy-barrier sequence, an image view and a sampler. The font's view and sampler become entry 0 of the renderer's texture list, which ImGui refers to as texture id 0.

Per-frame geometry

Each frame, all of ImGui's vertex and index lists are copied into a host-visible buffer pair that is persistently mapped (mapped once and never unmapped). There's one pair per swapchain image:

Why one pair per image? With two frames in flight (Chapter 9), the GPU may still be drawing the previous frame's UI while the CPU prepares this one. A single shared buffer would be overwritten while it's being read. This is a classic mistake when coming from OpenGL, and no validation layer reports it, because the write happens on the CPU. begin_frame has already waited for this image's previous use, so its own pair is free to rewrite, or even to replace with a larger one. The grass's indirect buffers follow the same rule.

Recording the draws

With the buffers filled, render binds them, sets the viewport and pushes the matrix, then walks ImGui's command lists:

Three things happen per command:

  • Texture. Id 0 is the font; ids 1 and up are extra images registered with the renderer. The texture is pushed as set 0 (Chapter 8) only when its image differs from the last one pushed.
  • Scissor. ImGui's clip rectangle is in logical points, so it's scaled by the framebuffer scale (2 on a Retina display) into pixels.
  • Draw. All lists share one vertex and one index buffer, so each draw adds the list's starting offsets to the command's own. ImGui uses 16-bit indices, hence UINT16 when the index buffer is bound.

Coming from OpenGL

This is the same loop as Dear ImGui's classic OpenGL backend (bind texture, glScissor, glDrawElementsBaseVertex) with one difference: when OpenGL code refilled a buffer the GPU was still reading, the driver quietly "orphaned" or renamed it behind the scenes. Here, that reuse is safe only because of the per-image buffers above.

Showing the shadow cascades

To show a GPU image in a window, it needs an entry in the texture list like the font's, registered under a texture id. The cascade panel does this for each layer of the shadow map:

Each cascade uses its own single-layer view of the shadow array (Chapter 10), sampled with the shadow sampler. The shadow map is a per-swapchain-image attachment, so shadow_texture_id points each cascade's texture id at this frame's view. Pushed descriptors are copied into the command buffer as it's recorded, so changing the entry can't disturb a frame in flight. By the UI pass the shadow map is already in its shader-readable layout, with fragment-shader read access established by the main pass. The UI pass declares that same read, so the scheduler sees the dependency and needs no additional barrier. The flipped UVs (uv0 at the bottom) turn the light's-eye view the right way up: the shadow projection has no Y flip (Chapter 11), so the light's "up" is stored at the bottom of the image.

Recap

  • Dear ImGui is immediate-mode: the UI is re-declared every frame, and ImGui returns plain 2-D triangle lists with per-command texture and clip rectangle.
  • The renderer draws them in the UI pass with a minimal pipeline: 20-byte vertices, a projection push constant, alpha blending, no depth.
  • Geometry goes into persistently mapped buffers, one pair per swapchain image, so the CPU never overwrites triangles a frame in flight is still drawing.
  • Any GPU image can be shown by registering it under a texture id, and each draw pushes the matching descriptor; the shadow cascades are displayed this way.
