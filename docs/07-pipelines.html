Pipelines and dynamic rendering

The single object that describes how a draw happens, from vertex layout to blending, and why Vulkan wants all of it decided up front.

Overview Source walkthrough Recap

Overview The big picture

In OpenGL, the way a draw call behaved depended on whatever state happened to be set at the time: which shader program was in use, whether blending was on, how depth testing compared, whether back faces were culled. You changed those with individual calls such as glEnable(GL_BLEND), and the driver worked out the consequences at draw time. Some combinations required it to quietly recompile your shaders, a common source of OpenGL's unpredictable hitches.

Vulkan gathers all of that into one immutable object, the graphics pipeline. You describe the shaders and most drawing state up front, and the driver builds a pipeline for that combination. At draw time you bind it. Some state can be declared dynamic and supplied in the command buffer; this renderer does that for the viewport and scissor. It keeps blending fixed, so objects with blending on and objects with blending off use different pipelines. Vulkan offers more dynamic state through optional features, but this renderer keeps those choices simple.

Its signature: the pipeline layout

A pipeline also needs to know the shape of the resources its shaders will read: which descriptor sets, and how many bytes of push constants (Chapter 6's three routes). That shape is a separate object, the pipeline layout. Think of it as a function signature: the layout lists the parameters, and at draw time you pass actual buffers and textures that fit it.

Dynamic rendering

With dynamic rendering, a pipeline declares only the formats of its attachments (the images it draws into, such as a colour image or a depth buffer), and you name the actual images when you start drawing. That's the feature Chapter 3 insisted on when choosing a GPU.

The cost: rebuilding when things change

Because a pipeline is baked, changing anything baked into it means building a new one. This renderer keeps the size of the window out of its pipelines (it's set per frame instead), so a resize does not require pipeline recreation. Rebuilding the swapchain and its images still costs time and requires waiting for GPU work to finish. But changing the anti-aliasing sample count, switching to wireframe, or a change in the screen's pixel format rebuilds every pipeline. A shared pipeline cache lets the driver reuse compilation work within a run when that happens.

Deeper dive

Most of the renderer's pipelines are built by one helper, Pipeline in src/graphics/pipeline.rs, used by materials, the sky and the grass. The shadow pass and ImGui build theirs directly with the same calls (Chapter 11, Chapter 15).

Creating the layout first

A Pipeline is made in two steps. The constructor creates only the layout:

The push-constant range is 144 bytes: two 4×4 matrices and a vec4, exactly the Push block of main.vert, visible to both shader stages. This is a renderer requirement, not a universal Vulkan allowance: Vulkan 1.3 guarantees only 128 bytes. Device selection checks max_push_constants_size and skips GPUs that cannot supply 144 bytes, with a diagnostic explaining why. A renderer supporting those GPUs would need a smaller block or a buffer for some data. set_layouts comes from the caller: for a material, set 0 is the global layout and, if it's textured, set 1 its texture layout (Chapter 8); the sky and grass pass their own. Three constructors choose the remaining options: new for ordinary materials (blending on), new_opaque for grass, and new_background for the sky, with no depth test, no blending and no wireframe.

Rasterizer and multisampling

  • polygon_mode switches to lines when the UI's wireframe toggle is on, unless this pipeline opted out (the sky would otherwise become a single outlined triangle). Vulkan requires fillModeNonSolid for line mode. Device creation enables it only when supported; the UI disables Wireframe on GPUs without it, and the toggle itself also guards against unsupported use.
  • Materials cull back faces (the sky and grass pass NONE), with counter-clockwise triangles counting as front. Which way round a triangle appears depends on the projection's Y direction, which differs from OpenGL's (Chapter 12).
  • rasterization_samples is the anti-aliasing setting. It must match the images being drawn into, which is why changing it rebuilds every pipeline.

Rust note · if is an expression

Rust has no ?: operator. Instead, if itself produces a value: polygon_mode: if wireframe { LINE } else { FILL }. The last expression in each block, written without a semicolon, is the value. Function bodies work the same way, which is why many functions in this codebase end with a bare value instead of return.

Blending and depth

When blending is enabled, this is classic "over" compositing: new colour × its alpha, plus existing colour × (1 − alpha). The colour write mask lets all four channels through either way.

Depth testing keeps the fragment nearest the camera (LESS). Depth runs from 0 at the near plane to 1 at the far: the viewport above sets min_depth 0 and max_depth 1, and the projection matrix must produce clip-space depth in 0..1, not OpenGL's −1..1 (Chapter 12). Each material decides whether it also writes depth.

Coming from OpenGL

Every struct on this page replaces a family of GL calls: glPolygonMode, glCullFace/glFrontFace, glEnable(GL_MULTISAMPLE), glBlendFunc/glBlendEquation, glDepthFunc/glDepthMask, glColorMask. The difference is when they take effect: once, at creation, instead of at every draw.

Putting it together

PipelineRenderingCreateInfo is the dynamic-rendering piece: one colour attachment in the swapchain's format, and a depth attachment in D32_SFLOAT. It's chained on through p_next by a raw pointer cast, the hand-written equivalent of push_next (Chapter 2). Creating a raw pointer is safe in Rust, but nothing ties its lifetime to rendering_info, so correctness rests on both being locals used immediately. render_pass is left null. Then everything is handed to create_graphics_pipelines, together with the shared cache. That call is where the driver compiles the SPIR-V for this exact combination of state, which is why it's comparatively slow and is never done mid-frame.

Rust note · two small idioms

iter().map(…).collect() transforms each element and gathers the results. The Vec<_> annotation on the variable tells collect what to build, and _ lets the compiler fill in the element type. zip walks two sequences in step, here pairing each stage with a mutable borrow of its own module info, which the stage info keeps pointing at.

create_graphics_pipelines can create many pipelines at once, so on failure ash returns a pair: the pipelines that did succeed, and the error. .map_err(|(_, e)| e) destructures that pair in the closure's parameter, discards the first part, and keeps the error so ? can return it.

Recap

  • A graphics pipeline bakes shaders and the state chosen to be fixed into one immutable object. Dynamic state is supplied when recording commands; changing baked state needs a new pipeline.
  • The pipeline layout is the resource signature: descriptor set layouts plus a 144-byte push-constant range.
  • Dynamic rendering replaces render passes and framebuffers; pipelines name only attachment formats.
  • Viewport and scissor are dynamic, so resizes don't rebuild pipelines. MSAA, wireframe and format changes do, triggered by a generation counter and done safely at a frame boundary.
